# Требования к развитию

Раздел содержит перспективные требования к Электронному журналу.

Наличие требования на этой странице не означает, что соответствующая
функция уже реализована. Фактическое состояние проекта приводится отдельно
в разделе «Состояние проекта».

## Статусы требований

| Статус | Значение |
|---|---|
| `READY` | Поведение подтверждено реализацией и проверками |
| `PARTIAL` | Реализована только часть требуемого поведения |
| `PLANNED` | Функция включена в целевую концепцию |
| `UNKNOWN` | Требование требует дополнительного уточнения |
| `REQUIRES DESIGN` | До реализации необходимо определить архитектуру и контракты |
| `REQUIRES AUDIT` | Имеющаяся реализация требует отдельной проверки |

## Подготовка учебного периода

Статус: `PLANNED`.

Перед началом семестра преподаватель должен иметь возможность:

- создать учебный год и семестр;
- указать дату начала и окончания семестра;
- настроить учебные недели;
- указать праздничные и неучебные дни;
- создать дисциплины;
- связать дисциплины с учебными группами;
- настроить расписание;
- импортировать списки групп из XLSX;
- сформировать модули;
- определить виды работ и их стоимость;
- настроить модели оценивания;
- создать индивидуальные планы студентов;
- сохранить контакты кураторов групп.

Праздничные дни должны учитываться при формировании расписания, перечня
занятий и ожидаемых результатов.

## Проведение занятия

Статус: `PLANNED`.

Целевой сценарий включает:

1. открытие занятия;
2. отображение списка студентов;
3. отметку присутствующих;
4. завершение переклички;
5. переход в режим фиксации опозданий;
6. ввод результатов учебной работы;
7. фиксацию событий, замечаний и комментариев;
8. завершение занятия.

Операции, выполняемые во время пары, должны требовать минимального
количества действий со стороны преподавателя.

## Посещаемость и опоздания

Статус: `PLANNED`.

По умолчанию студент может считаться отсутствующим до подтверждения его
присутствия преподавателем.

После завершения переклички приложение должно:

- сохранять момент окончания отметки присутствующих;
- автоматически рассчитывать продолжительность опоздания;
- использовать часы текущего устройства;
- позволять изменить статус отсутствия при получении подтверждающих
  сведений;
- хранить причину изменения;
- при необходимости прикладывать подтверждающий файл или изображение.

Модель посещаемости должна различать присутствие, опоздание, отсутствие
без подтверждённой причины и отсутствие по подтверждённой причине.

## Рассадка и события на занятии

Статус: `REQUIRES DESIGN`.

В перспективной версии рассматриваются:

- схема аудитории;
- фиксация мест студентов;
- выбор студента по месту в аудитории;
- настраиваемые категории положительных событий;
- настраиваемые категории нарушений;
- быстрый ввод события в один или два действия;
- визуальное различение категорий событий;
- история событий по студенту.

Правила автоматического влияния дисциплинарных событий на результат
занятия должны быть прозрачными, настраиваемыми и сохраняться вместе с
применённым решением.

## Модель оценивания

Статус: `PLANNED`.

Правила оценивания должны поддерживаться на двух уровнях:

1. правила дисциплины по умолчанию;
2. переопределения для конкретного занятия.

Система должна учитывать:

- произвольные числовые шкалы;
- традиционные оценки;
- результаты «зачтено» и «не зачтено»;
- первичные и итоговые баллы;
- стоимость отдельных работ;
- модульное суммирование;
- пороги итоговых результатов;
- несколько попыток сдачи;
- отсутствие результата;
- изменяемые критерии проверки.

После фиксации результата должна сохраняться применённая модель
оценивания или её неизменяемый снимок. Последующее изменение настроек не
должно менять исторические результаты автоматически.

## Лабораторные работы и рубежные контроли

Статус: `PLANNED`.

Для лабораторных работ требуется различать:

- присутствие на занятии;
- выполнение работы;
- защиту работы;
- результат отдельной попытки.

Планируются:

- изменяемые чек-листы защиты;
- бинарные критерии «да/нет»;
- таймер защиты;
- предупреждение об окончании времени;
- фиксация дополнительного вопроса;
- история попыток;
- импорт первичных и итоговых результатов из внешних программ.

Рубежные контроли и тесты должны поддерживать собственные правила
начисления и суммирования баллов.

## Консультации

Статус: `PLANNED`.

Консультация рассматривается как отдельное учебное событие, которое может
не относиться к одной конкретной группе.

Во время консультации преподаватель должен иметь возможность:

- найти студента по имени и группе;
- указать цель посещения;
- зафиксировать защиту лабораторной работы;
- зарегистрировать пересдачу;
- отметить выполнение этапов индивидуального плана;
- сохранить текстовый комментарий;
- зарегистрировать консультацию текущими датой и временем.

## Индивидуальные планы

Статус: `PLANNED`.

Индивидуальный план может использоваться для:

- курсовых работ;
- выпускных квалификационных работ;
- проектных работ;
- иных индивидуальных заданий.

План должен включать:

- список этапов;
- отметку выполнения этапов;
- комментарии к консультациям;
- историю изменений;
- возможность добавления дополнительных встреч.

## Отчётность

Статус: `PLANNED`.

Планируется формирование:

- журнала за семестр;
- журнала за учебный год;
- отчёта по посещаемости;
- отчёта по успеваемости;
- отчёта по конкретному студенту;
- списка задолженностей;
- списка студентов с высокими результатами;
- отчёта для куратора;
- сводного отчёта для подразделения;
- отчёта по индивидуальному плану;
- перечня проведённых занятий;
- истории событий и замечаний.

Основным форматом готового отчётного документа предполагается PDF.

Для дальнейшей обработки данных предусматриваются XLSX и текстовые
форматы.

При формировании отчёта преподаватель выбирает независимую карточку
реквизитов. Карточка не входит в структуру журнала и используется только
как источник данных для оформления документа.

## Карточки реквизитов

Статус: `PLANNED`.

Приложение должно предоставлять отдельное хранилище именованных карточек
реквизитов.

Карточка может содержать:

- ФИО преподавателя;
- наименование организации;
- подразделение;
- должность;
- контактные сведения;
- дополнительные пользовательские поля.

Карточки:

- не принадлежат учебному году;
- не связаны с дисциплинами и группами;
- не участвуют в ведении журнала;
- выбираются только при формировании отчёта;
- могут использоваться повторно для разных документов.

Сформированный отчёт должен сохранять снимок использованных реквизитов.

## Импорт и экспорт

Статус: `REQUIRES AUDIT`.

Импорт из XLSX требуется для загрузки списков групп и иных данных,
получаемых из внешних систем.

Экспорт должен поддерживать:

- ручной перенос данных между устройствами;
- резервное копирование;
- подготовку данных для внешней обработки;
- формирование отчётных файлов.

Форматы, схемы файлов и правила разрешения конфликтов должны быть описаны
отдельными контрактами.

## Синхронизация устройств

Статус: `REQUIRES DESIGN`.

Базовым способом переноса данных остаются импорт, экспорт и резервные
копии.

Перспективная синхронизация через локальную сеть должна учитывать:

- обнаружение устройств;
- выбор источника истины;
- версии записей;
- конфликты изменений;
- повторную передачу;
- защиту соединения;
- журнал синхронизации;
- восстановление после разрыва связи.

Рассматриваются два варианта:

1. синхронизация независимых копий журнала;
2. использование компьютера как основного узла, к которому подключается
   мобильное устройство.

Окончательный вариант пока не определён.

## Хранение и загрузка данных

Статус: `PLANNED`.

Целевым серверным хранилищем рассматривается PostgreSQL.

Одновременно в интерфейсе активен один учебный год, однако приложение не
должно загружать весь год в оперативную память.

Требуются:

- выборочная загрузка данных;
- фильтрация запросов по учебному году и семестру;
- ограниченная загрузка связанных объектов;
- постраничное отображение больших списков;
- индексы по основным полям выборки;
- ограниченный временный кэш;
- освобождение данных после смены рабочего контекста.

Архивные годы остаются в хранилище и доступны по запросу.

## Произвольные выборки

Статус: `REQUIRES DESIGN`.

Требуется возможность получать нестандартные выборки из накопленных
данных.

Прямой ввод SQL-запросов может создать риски безопасности и связать
пользовательский интерфейс с внутренней структурой базы данных.

Возможные решения:

- конструктор отчётов;
- сохранённые фильтры;
- режим запросов только для чтения;
- ограниченный набор разрешённых операций;
- экспорт результата в текстовый или табличный формат.
