# Правила написания

Эта страница определяет требования к содержанию и формулировкам документации
DigitalDiaryApp.

Цель правил — сохранять различие между фактической реализацией, требованиями
к продукту и неподтверждёнными предположениями, уменьшать дублирование и
улучшать поиск по документации.

## Статусы проекта

Для компонентов кода используются стандартизированные состояния реализации,
проверки и документации.

Правила выбора статусов, автоматического обнаружения новых папок и файлов,
а также объединения автоматической и ручной оценки приведены на странице
[«Статусы проекта»](statuses.md).

## Фактическое состояние и перспективные требования

Описание текущей реализации должно основываться на подтверждённом состоянии
исходного кода, тестов или других проверяемых источников проекта.

Перспективные требования должны быть явно отделены от существующего
функционала.

Рекомендуемые формулировки для будущих возможностей:

- «планируется»;
- «перспективное требование»;
- «предполагается в дальнейшем»;
- «не реализовано в текущем baseline».

Не следует объединять реализованные и перспективные возможности в одном
перечне без явного обозначения их статуса.

Статус `PLANNED` допускается использовать как компактное формальное обозначение
перспективного требования.

## Стиль документации

Основной язык документации — русский.

Текст должен быть:

- нейтральным;
- официально-деловым;
- технически точным;
- ориентированным на текущее состояние проекта;
- свободным от внутренней истории обсуждений и разработки.

Не следует использовать формулировки:

```text
мы сделали
мы решили
нам нужно
в этой лабораторной работе
здесь я добавил
потом надо переделать
```

Предпочтительны формулировки:

```text
компонент выполняет
раздел описывает
реализация поддерживает
требование предусматривает
подсистема требует дополнительного аудита
```

История появления решения описывается только тогда, когда она необходима
для понимания архитектурного ограничения или принятого технического решения.

## Технические идентификаторы

Имена классов, функций, методов, схем, полей и модулей сохраняются в форме,
используемой в исходном коде.

Примеры:

```text
OrmService
LessonUpdateSchema
ScheduleGroupLink
auto_commit
app.services
```

При первом существенном упоминании предметного объекта рекомендуется связывать
пользовательский и технический термин.

Например:

```text
студент (`Student`)
занятие (`Lesson`)
оценка (`Mark`)
посещаемость (`Attendance`)
```

Это улучшает поиск как по предметным, так и по программным названиям.

## Заголовки и структура текста

Заголовок страницы должен прямо называть описываемую тему.

Предпочтительно:

```markdown
# Транзакции
# Обмен данными
# Записи занятия
```

Не рекомендуется:

```markdown
# Некоторые особенности
# Дополнительная информация
# Разное
```

Страница должна начинаться с краткого объяснения того, что на ней описано и
какую задачу она решает.

Следует избегать длинных вводных разделов об истории появления страницы.

### Когда использовать таблицу

Таблица предпочтительна, если требуется сопоставить однотипные свойства:

- поле и его назначение;
- операция и результат;
- изменение и связанный раздел документации;
- сущность и ограничение.

### Когда использовать список

Список используется для независимых пунктов, которые не требуют сопоставления
по нескольким колонкам.

### Когда использовать admonition

Admonition используется для информации, которую важно визуально отделить от
основного текста:

- критическое ограничение;
- предупреждение;
- принцип;
- неподтверждённое состояние;
- практическое правило.

Не следует превращать большую часть страницы в последовательность admonition-
блоков.

## Ссылки между страницами

Если информация уже имеет канонический источник, вместо повторения большого
фрагмента используется краткое пояснение и ссылка.

Пример:

```markdown
Подробный состав полей приведён на странице
[«Модели данных»](../../architecture/models.md).
```

Относительные ссылки должны вести на исходные документы, а не на
сгенерированные HTML-файлы.

Не следует использовать ссылки на:

```text
docs/build/
*.html
локальные абсолютные пути пользователя
```

Точные API-детали следует связывать с разделом
[«API»](../../api/index.md), а архитектурное объяснение — с соответствующей
страницей раздела [«Архитектура»](../../architecture/index.md).

## Дублирование информации

Перед добавлением подробного описания необходимо проверить, существует ли уже
каноническая страница для этого факта.

Допустимо повторить:

- краткое определение, необходимое для понимания текущего контекста;
- название ограничения;
- короткую сводку перед ссылкой на подробности.

Не следует повторять:

- полные таблицы полей;
- одинаковые перечни ограничений;
- большие описания одного сервиса;
- одни и те же результаты проверок;
- один и тот же набор требований.

Если две страницы начинают отвечать на один и тот же вопрос, следует выбрать
одну каноническую страницу и заменить подробности на другой странице ссылкой.

## Формулирование ограничений

Ограничение должно описывать наблюдаемое поведение и его область действия.

Предпочтительно:

```text
Для `Mark` сервис обновления применяет только поле `data`.
```

Менее полезно:

```text
Обновление оценок ограничено.
```

Если существует расхождение между слоями, следует называть оба слоя.

Например:

```text
`LessonUpdateSchema` принимает `schedule_id` и `date`, однако фактический
сервисный контракт обновления не применяет эти поля как обычные изменяемые
значения.
```

## Подготовка текста для поиска

Поиск должен находить страницу независимо от того, использует пользователь
предметный или технический термин.

Для ключевых сущностей рекомендуется естественно упоминать оба варианта:

```text
учебная группа (`Group`)
расписание (`Schedule`)
комментарий (`Comment`)
```

Не требуется искусственно перечислять возможные синонимы в каждом абзаце.
Дополнительные пользовательские термины следует добавлять только тогда, когда
они действительно употребляются в проекте или интерфейсе.

Заголовки должны быть содержательными, поскольку они используются поиском и
навигацией.

Не рекомендуется использовать несколько одинаковых заголовков на одной
странице без необходимости. Если повторение неизбежно, заголовок следует
уточнить контекстом.

## Пример разделения информации

Для сущности `Student` сведения распределяются следующим образом:

| Вопрос | Каноническое место |
|---|---|
| Что означает студент в предметной области | О проекте |
| Какие поля и связи имеет `Student` | Архитектура |
| Как выглядит точный Python-класс | API |
| Какие проблемы реализации подтверждены проверками | Состояние |
| Как разработчику проверить изменение | Разработка |

Такое разделение позволяет одной сущности присутствовать в нескольких
разделах без дублирования одного и того же содержания.
