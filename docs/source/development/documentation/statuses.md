# Статусы проекта

Страница определяет компактную систему оценки состояния основных компонентов
DigitalDiaryApp.

Статусы предназначены для быстрой оценки проекта и применяются к крупным
логическим группам кода: моделям, схемам, сервисам, подсистемам ввода-вывода,
инфраструктурным сервисам и другим самостоятельным компонентам.

Система должна оставаться полезной даже тогда, когда разработчик не обновил
документацию или ручную сводку состояния.

:::{admonition} Основной принцип
:class: important

**Отсутствие ручного статуса не должно скрывать существующий или новый код.**

При сборке документации автоматический анализ формирует базовую оценку, а
ручные данные только уточняют или переопределяют её.
:::

## Состояние реализации

| Статус | Значение | Когда используется |
|---|---|---|
| `PLANNED` | Планируется | Кода ещё нет; возможность относится к будущему развитию; компонент существует только как требование |
| `IN PROGRESS` | В работе | Код уже появился; реализация ещё меняется; добавлен новый непроверенный файл; контракт реализован не полностью |
| `READY` | Готово | Компонент реализован; используется текущим приложением; основной контракт считается завершённым |
| `INACTIVE` | Неактивно | Код сохранился, но не участвует в подтверждённых сценариях; старый компонент заменён; обнаружен рудимент |

`INACTIVE` не означает автоматически, что код можно безопасно удалить.
Перед удалением требуется проверить импорты, динамические вызовы и внешние
зависимости.

Примеры:

```text
Модели             READY
Новый сервис       IN PROGRESS
LAN-синхронизация  PLANNED
Старый helper      INACTIVE
```

## Состояние проверки

| Статус | Значение | Когда используется |
|---|---|---|
| `UNVERIFIED` | Не проверено | Код только написан; тесты после изменения не запускались; новый компонент найден автоматически |
| `TESTED` | Протестировано | Релевантные автоматизированные тесты успешно проходят; изменение проверено тестами; регрессионная проверка успешна |
| `PRODUCT VERIFIED` | Проверено в продукте | Сценарий выполнен через приложение; проверена интеграция соседних слоёв; результат подтверждён в конечном пользовательском сценарии |

Типовая последовательность:

```text
Код написан
    ↓
UNVERIFIED
    ↓
Релевантные автоматизированные тесты прошли
    ↓
TESTED
    ↓
Сценарий проверен в работающем приложении
    ↓
PRODUCT VERIFIED
```

Успешный импорт, запуск интерпретатора или отсутствие синтаксической ошибки
сами по себе не означают `TESTED`.

`PRODUCT VERIFIED` не назначается автоматически только по результату unit- или
backend-тестов.

## Состояние документации

| Статус | Значение | Когда используется |
|---|---|---|
| `MISSING` | Отсутствует | Для нового компонента нет подходящей страницы; новое поведение нигде не описано |
| `DRAFT` | Требует обновления | Описание существует, но код изменился; страница ещё готовится; соответствие реализации не подтверждено |
| `CURRENT` | Актуально | Страница сверена с текущим состоянием компонента; связанные ограничения и контракты отражены в документации |

Если компонент изменился после последнего подтверждения документации,
автоматическая оценка может понизить состояние с `CURRENT` до `DRAFT`.

## Дополнительные флаги

| Флаг | Когда используется |
|---|---|
| `REQUIRES AUDIT` | Фактический контракт недостаточно исследован; необходим отдельный аудит реализации или тестов |
| `KNOWN ISSUE` | Подтверждена конкретная воспроизводимая проблема или известное ограничение |

`REQUIRES AUDIT` означает недостаток подтверждённой информации.
`KNOWN ISSUE` означает, что конкретная проблема уже установлена.

## Источник состояния

| Источник | Значение |
|---|---|
| `AUTO` | Значение получено автоматическим анализом |
| `MANUAL` | Значение подтверждено или переопределено человеком |
| `NEW` | Компонент или файл обнаружен после принятой базовой точки |

Ручная информация имеет приоритет при формировании итогового статуса, но не
может скрыть автоматически обнаруженное изменение.

## Автоматическое обнаружение изменений

Автоматический анализ выполняется при сборке документации и должен обнаруживать
изменения независимо от того, обновлял ли разработчик ручную сводку.

Применяются следующие правила:

1. Если появляется новая ранее неизвестная папка, единицей нового состояния
   становится вся папка.
2. Пока папка имеет состояние `NEW`, отдельные новые файлы внутри неё не
   перечисляются.
3. Если папка уже известна системе, новые файлы внутри неё отображаются
   отдельно.
4. Новый файл в известной группе может временно понизить агрегированное
   состояние группы до более осторожной оценки.
5. После классификации новой папки последующие новые файлы внутри неё
   отслеживаются отдельно.
6. Служебные файлы и каталоги не участвуют в оценке.

Пример новой папки:

```text
app/reports/
├── builder.py
├── exporter.py
└── schemas.py
```

Она отображается одной записью:

```text
NEW app/reports/

Реализация:   IN PROGRESS
Проверка:     UNVERIFIED
Документация: MISSING
```

Если же в уже известной группе появляется:

```text
app/services/report.py
```

dashboard показывает новый файл отдельно и пересчитывает агрегированное
состояние группы `services`.

По умолчанию игнорируются как минимум:

```text
__pycache__/
__init__.py
*.pyc
```

## Полуавтоматическое формирование состояния

Итоговая сводка строится в следующем порядке:

```text
Файловая система + Git + результаты проверок + документация
                         ↓
               автоматическое обнаружение
                         ↓
                автоматическая оценка
                         ↓
                  ручные уточнения
                         ↓
                  итоговый статус
                         ↓
                dashboard документации
```

Автоматическая оценка является значением по умолчанию.

Ручная сводка используется только для уточнений, флагов, планируемых
компонентов и подтверждений, которые невозможно надёжно получить
автоматически. Она не является обязательным реестром существующих компонентов.

Если автоматике недостаточно данных, выбирается более осторожное состояние,
а не более высокий неподтверждённый статус.
