# Сопровождение документации

Страница определяет, какие изменения проекта требуют пересмотра документации
DigitalDiaryApp и что необходимо проверить перед завершением работы.

Документация сопровождается вместе с исходным кодом. Изменение реализации,
контракта, пользовательского поведения или подтверждённого состояния проекта
должно приводить к проверке связанных канонических страниц.

## Общий принцип

Изменение кода не означает автоматическую необходимость переписывать всю
документацию.

Необходимо определить:

1. какой компонент изменился;
2. изменился ли его внешний или архитектурный контракт;
3. какой раздел является каноническим источником для этого факта;
4. требуется ли обновить состояние проекта;
5. какие проверки необходимо выполнить перед коммитом.

Если изменение не влияет на документируемый контракт, достаточно убедиться,
что существующее описание остаётся корректным.

## Что обновлять при изменении проекта

| Изменение | Что проверить в документации |
|---|---|
| SQLAlchemy-модель | `architecture/models.md`, API моделей, связанные ограничения и связи |
| Pydantic-схема | `architecture/schemas.md`, API схем, правила валидации и изменяемые поля |
| Сервис сущности | `architecture/services.md`, API сервисов, CRUD-контракты и ограничения |
| `OrmService` | `architecture/ormservice.md`, транзакционные и маршрутизирующие контракты |
| `app/io_tools` | состояние проекта, будущая документация обмена данными, известные ограничения |
| Новый верхнеуровневый компонент `app/` | автоматическая сводка состояния, канонический архитектурный раздел, API при наличии публичных объектов |
| Новый файл в известной группе | состояние родительской группы и соответствующая архитектурная страница |
| Пользовательский сценарий | продуктовая документация, будущие требования и UI-документация при наличии |
| Перспективная функция | `project/future.md`, без представления её как текущей реализации |
| Ограничение или подтверждённая ошибка | раздел «Состояние» и каноническая техническая страница |
| Команда запуска или разработки | соответствующая страница раздела «Разработка» |
| Структура документации | `development/documentation/structure.md` и связанные точки входа |

Точные Python-классы и методы не следует вручную дублировать в архитектурных
страницах, если они уже доступны через API reference.

## Изменение моделей

При изменении SQLAlchemy-модели проверяются:

- состав полей;
- nullable и default-поведение;
- внешние ключи;
- отношения;
- уникальные ограничения;
- наследуемые поля;
- связанные схемы;
- сервисные операции, если изменение влияет на контракт.

Если добавлено внутреннее поле, которое не влияет на предметный или публичный
контракт, достаточно проверить, требуется ли его отражение в
`architecture/models.md` и API.

## Изменение схем

При изменении Pydantic-схемы проверяются:

- допустимые входные поля;
- обязательность полей;
- ограничения значений;
- Create/Filter/Update/Delete-контракты;
- соответствие фактическому поведению сервиса.

Наличие поля в `UpdateSchema` не должно автоматически документироваться как
поддерживаемая операция обновления, если сервис фактически его не применяет.

## Изменение сервисов

Для сервисов необходимо проверить:

- поддерживаемые операции;
- способ поиска объектов;
- ограничения create/update/delete;
- возвращаемые значения;
- исключения и ошибки;
- взаимодействие с `OrmService`;
- влияние на транзакционный контракт.

Если сервис изменён, но его внешнее поведение осталось прежним, архитектурная
страница может не требовать изменения. Это необходимо подтвердить проверкой
существующего текста.

## Изменение `OrmService`

`OrmService` является инфраструктурным фасадом, поэтому его изменение может
затрагивать несколько разделов одновременно.

Проверяются:

- регистрация сервисов;
- маршрутизация объектов и схем;
- управление session;
- commit и rollback;
- CRUD-операции;
- импорт и экспорт;
- автоматическое обнаружение сервисов;
- связанные API reference страницы.

Изменение внутренней реализации не должно приводить к описанию нового
контракта, если наблюдаемое поведение не изменилось.

## Новые компоненты и файлы

Система состояния проекта автоматически обнаруживает новые элементы.

Если появляется новая неизвестная папка, она отображается как единый новый
компонент.

Если новый файл появляется внутри известной группы, он отображается отдельно
и может временно понизить агрегированное состояние родительского компонента.

После такого обнаружения необходимо решить:

- относится ли новая область к существующему компоненту;
- требуется ли отдельная архитектурная страница;
- должен ли компонент получить ручное имя или override;
- есть ли связанная документация;
- выполнены ли релевантные тесты.

Автоматическое обнаружение не заменяет дальнейшую классификацию, но не
позволяет новому коду остаться незаметным.

## Изменение перспективных требований

Перспективное требование обновляется в `project/future.md`.

Если функция была реализована, необходимо:

1. проверить фактическое поведение;
2. перенести её описание в соответствующий канонический раздел;
3. убрать формулировки, представляющие её только как будущую возможность;
4. обновить состояние компонента;
5. сохранить в future-разделе только действительно остающуюся перспективную
   часть.

Факт существования прототипа или незавершённого кода сам по себе не означает,
что требование стало реализованным.

## Известные проблемы и аудит

Если обнаружена конкретная воспроизводимая проблема, используется флаг
`KNOWN ISSUE`.

Если поведение ещё недостаточно исследовано, используется `REQUIRES AUDIT`.

Перед снятием этих флагов требуется фактическое подтверждение:

- аудит исходного кода;
- релевантные тесты;
- проверка пользовательского или интеграционного сценария, если это необходимо.

Флаг не снимается только потому, что код был изменён.

## Состояние документации после изменения кода

После изменения компонента состояние его документации должно отражать
фактическую актуальность.

Типовая логика:

```text
Код не изменялся после подтверждения документации
→ CURRENT

Код изменился, соответствие текста ещё не проверено
→ DRAFT

Для нового компонента документации нет
→ MISSING
```

После сверки и необходимого обновления документация может снова получить
`CURRENT`.

## Definition of Done

Изменение, затрагивающее документируемый контракт, считается завершённым,
когда выполнены следующие условия:

- реализация находится в ожидаемом состоянии;
- релевантные тесты выполнены или состояние проверки явно обозначено;
- автоматическая сводка не содержит необъяснённых изменений;
- канонические страницы проверены и при необходимости обновлены;
- перспективные и фактические сведения разделены;
- известные проблемы или области аудита обозначены;
- `git diff --check` не сообщает ошибок;
- строгая Sphinx-сборка с `-W` проходит успешно;
- изменённые страницы проверены визуально;
- `git status --short` не содержит временных файлов.

Если хотя бы один пункт неприменим к конкретному изменению, его можно
пропустить только осознанно.

## Минимальный порядок сопровождения

Для обычного изменения кода используется последовательность:

```text
Изменение кода
      ↓
Автоматическое обнаружение состояния
      ↓
Определение затронутого компонента
      ↓
Проверка канонической документации
      ↓
Обновление текста или подтверждение его актуальности
      ↓
Проверка тестов и статусов
      ↓
Строгая сборка документации
      ↓
Коммит
```

Подробные команды проверки приведены на странице
[«Проверка документации»](verification.md).
