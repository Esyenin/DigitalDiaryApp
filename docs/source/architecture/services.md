(architecture-services)=
# Сервисы сущностей

Раздел описывает сервисный слой пакета `app.services`, расположенный между
Pydantic-схемами и фасадом `OrmService`.

Сервисы сущностей не выполняют SQL-запросы самостоятельно. Они проверяют
входные данные, создают ORM-объекты, строят SQLAlchemy-выражения и
применяют допустимые изменения к уже загруженным объектам.

## Состав сервисного слоя

| Сервис | Модель |
|---|---|
| `GroupService` | `Group` |
| `StudentService` | `Student` |
| `ScheduleService` | `Schedule` |
| `ScheduleGroupLinkService` | `ScheduleGroupLink` |
| `LessonService` | `Lesson` |
| `AttendanceService` | `Attendance` |
| `MarkService` | `Mark` |
| `CommentService` | `Comment` |

Все перечисленные классы наследуются от `BaseService`.

## Ответственность `BaseService`

`BaseService` связывает одну SQLAlchemy-модель с четырьмя Pydantic-схемами:

| Атрибут | Назначение |
|---|---|
| `model` | Класс SQLAlchemy-модели |
| `create_schema` | Схема создания |
| `select_schema` | Схема фильтрации |
| `update_schema` | Схема обновления |
| `delete_schema` | Схема удаления |

Дополнительные параметры:

| Атрибут | Назначение |
|---|---|
| `schema_fields` | Поля ORM-объекта, которые разрешено извлекать для обработки |
| `update_lookup_fields` | Поля идентификации, которые нельзя изменять через сервис |

По умолчанию `update_lookup_fields` содержит только `id`.

## Допустимые входные данные

Методы базового сервиса принимают:

- экземпляр Pydantic-схемы;
- ORM-объект;
- объект `Mapping`, включая обычный словарь;
- `None` для поиска без фильтра.

Перед обработкой данные преобразуются в словарь.

Для Pydantic-схем учитываются только поля, переданные явно. Для
ORM-объектов извлекаются публичные атрибуты, ограниченные набором
`schema_fields`.

## Валидация

Проверка выполняется через схему, соответствующую операции.

При успешной валидации сервис продолжает обработку. При
`pydantic.ValidationError` сервис:

1. записывает предупреждение в журнал;
2. не выбрасывает исключение наружу;
3. возвращает `None`.

Следовательно, вызывающий слой обязан отличать допустимый результат от
`None`, означающего отклонённые данные.

Иные исключения, возникающие внутри пользовательских валидаторов, должны
рассматриваться отдельно в соответствии с фактическим поведением
Pydantic.

## Создание ORM-объекта

Основной метод: `create_instance()`.

Совместимый короткий вызов: `create()`.

Порядок обработки:

```text
Входные данные
      ↓
Преобразование в словарь
      ↓
Проверка схемой создания
      ↓
Создание ORM-объекта
```

Если передан уже созданный объект требуемой SQLAlchemy-модели и его данные
проходят валидацию, возвращается исходный объект.

Метод не добавляет объект в сессию и не подтверждает транзакцию.

## Построение выборки

Основной метод: `build_select()`.

Совместимый короткий вызов: `get()`.

Метод возвращает SQLAlchemy-выражение `Select`.

При `filters=None` строится запрос без условий:

```text
select(Model)
```

При наличии фильтра данные проходят соответствующую схему и передаются в
`filter_by()`.

Метод не выполняет построенный запрос.

## Применение обновления

Основной метод: `apply_update()`.

Совместимый короткий вызов: `update()`.

Метод принимает:

1. существующий ORM-объект;
2. данные обновления.

После валидации сервис присваивает значения непосредственно атрибутам
ORM-объекта.

Поля из `update_lookup_fields` пропускаются даже в том случае, если схема
обновления их принимает.

Метод возвращает тот же ORM-объект после изменения либо `None`, если:

- объект относится к другой модели;
- данные обновления не прошли валидацию.

Метод не выполняет `flush()` или `commit()`.

## Построение удаления

Основной метод: `build_delete()`.

Совместимый короткий вызов: `delete()`.

Метод возвращает SQLAlchemy-выражение `Delete`, сформированное через
`filter_by()`.

Схемы удаления требуют непустой фильтр, поэтому операция удаления без
явного критерия отклоняется.

Метод не выполняет построенное выражение.

## Матрица сервисов

| Сервис | `schema_fields` | Неизменяемые поля |
|---|---|---|
| `GroupService` | `name`, `speciality` | `id` |
| `StudentService` | `group_id`, `surname`, `first_name`, `patronymic`, `personal_data`, `bmstu_email` | `id` |
| `ScheduleService` | `odd_or_even`, `type`, `is_assessment`, `day`, `time` | `id` |
| `ScheduleGroupLinkService` | `group_id`, `schedule_id` | обновление отклоняется схемой |
| `LessonService` | `schedule_id`, `topic`, `date` | `id`, `schedule_id`, `date` |
| `AttendanceService` | `student_id`, `lesson_id`, `is_visited` | `id`, `student_id`, `lesson_id` |
| `MarkService` | `student_id`, `lesson_id`, `data` | `id`, `student_id`, `lesson_id` |
| `CommentService` | `student_id`, `lesson_id`, `data` | `id`, `student_id`, `lesson_id` |

## `GroupService`

Сервис связывает `Group` со схемами группы.

Поддерживаемое обновление:

- `name`;
- `speciality`.

Изменение `id` запрещено базовым контрактом.

Уникальность названия группы проверяется базой данных, а не сервисом.

## `StudentService`

Сервис связывает `Student` со схемами студента.

Поддерживаемое обновление:

- `group_id`;
- `surname`;
- `first_name`;
- `patronymic`;
- `personal_data`;
- `bmstu_email`.

Перенос студента в другую группу допускается текущим сервисным
контрактом через изменение `group_id`.

## `ScheduleService`

Сервис связывает `Schedule` со схемами расписания.

Поддерживаемое обновление:

- `odd_or_even`;
- `type`;
- `is_assessment`;
- `day`;
- `time`.

Сервис не ограничивает строковые значения перечислениями. Такие
ограничения отсутствуют и в текущих схемах.

## `ScheduleGroupLinkService`

Сервис связывает `ScheduleGroupLink` со схемами ассоциативной модели.

Создание, поиск и удаление поддерживаются.

Обновление запрещено `ScheduleGroupLinkUpdateSchema`. Для изменения связи
необходимо удалить существующую запись и создать новую.

Уникальность сочетания группы и расписания обеспечивается ограничением
базы данных.

## `LessonService`

Сервис связывает `Lesson` со схемами занятия.

`LessonUpdateSchema` принимает:

- `schedule_id`;
- `topic`;
- `date`.

Однако `LessonService.update_lookup_fields` содержит `schedule_id` и
`date`. Поэтому при фактическом применении обновления изменяется только
`topic`.

Это является важным различием между контрактом схемы и поведением
сервиса.

## `AttendanceService`

Сервис связывает `Attendance` со схемами посещаемости.

При обновлении неизменяемыми остаются:

- `student_id`;
- `lesson_id`.

Изменяется только `is_visited`.

Для переноса записи посещаемости к другому студенту или занятию требуется
удаление и повторное создание записи.

## `MarkService`

Сервис связывает `Mark` со схемами оценки.

При обновлении изменяется только `data`.

Связи со студентом и занятием являются полями идентификации и не
изменяются.

Диапазон значения оценки сервисом не проверяется.

## `CommentService`

Сервис связывает `Comment` со схемами комментария.

При обновлении изменяется только `data`.

Связи со студентом и занятием не изменяются.

## Граница транзакции

Сервисы сущностей не отвечают за:

- создание SQLAlchemy-сессии;
- выполнение `Select` и `Delete`;
- добавление объектов в сессию;
- `flush()`;
- `commit()`;
- `rollback()`;
- закрытие сессии.

Эти обязанности выполняет `OrmService`.

Такое разделение позволяет использовать сервисы для подготовки операций
без неявного изменения состояния базы данных.

## Контракт результата

Методы сервисов используют следующий общий подход:

| Операция | Успешный результат | Отклонённые данные |
|---|---|---|
| создание | ORM-объект | `None` |
| поиск | `Select` | `None` |
| обновление | изменённый ORM-объект | `None` |
| удаление | `Delete` | `None` |

Контракт требует обязательной проверки результата вызывающим кодом.

## Известные ограничения

### Подавление ошибок валидации

`ValidationError` преобразуется в `None`. Причина отказа доступна через
журналирование, но не возвращается как типизированный результат операции.

### Неодинаковая изменяемость полей

Состав полей схемы обновления и фактически изменяемых полей может
различаться из-за `update_lookup_fields`.

### Бизнес-ограничения

Сервисный слой не добавляет ограничения, отсутствующие в схемах и базе
данных. В частности, он не проверяет:

- диапазон оценки;
- допустимые значения расписания;
- формат электронной почты;
- перспективные правила оценивания.

### Ошибки базы данных

Уникальность, внешние ключи и другие ограничения базы данных проявляются
только при выполнении выражений и синхронизации с сессией. Их обработка
находится на уровне `OrmService`.
