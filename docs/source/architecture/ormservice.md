(architecture-ormservice)=
# OrmService

`OrmService` является фасадом верхнего уровня для работы с SQLAlchemy-моделями
через единый интерфейс.

Он автоматически обнаруживает сервисы сущностей, определяет подходящий сервис
по входным данным, выполняет CRUD-операции, управляет SQLAlchemy-сессией и
предоставляет интеграцию с XLSX-импортом и экспортом.

## Основная ответственность

`OrmService` отвечает за:

- получение или создание SQLAlchemy-сессии;
- автоматическое обнаружение сервисов сущностей;
- регистрацию сервисов по моделям и Pydantic-схемам;
- определение сервиса по переданному объекту;
- выполнение операций создания, чтения, обновления и удаления;
- управление `flush`, `commit`, `rollback` и `close`;
- обработку ошибок SQLAlchemy;
- журналирование операций;
- передачу данных в подсистему XLSX-импорта и экспорта.

Сервисы сущностей при этом остаются ответственными только за валидацию,
создание ORM-объектов и построение SQLAlchemy-выражений.

## Инициализация

Конструктор принимает:

| Параметр | Назначение |
|---|---|
| `session` | Готовая SQLAlchemy-сессия |
| `session_factory` | Фабрика для создания сессии |
| `auto_commit` | Выбор между автоматическим `commit()` и `flush()` |
| `close_on_exit` | Закрытие сессии при выходе из context manager |
| `service_logger` | Пользовательский объект `logging.Logger` |

Необходимо передать либо `session`, либо `session_factory`.

Если оба значения отсутствуют, выбрасывается `OrmServiceError`.

Если переданы оба значения, используется готовая `session`.

## Автоматическое обнаружение сервисов

При инициализации фасад просматривает пакет `app.services`.

Из обхода исключаются:

```text
base
ormservice
__init__
```

Остальные модули импортируются динамически.

К регистрации допускаются классы, которые:

- наследуются от `BaseService`;
- объявлены непосредственно в рассматриваемом модуле;
- имеют заданный атрибут `model`.

Для каждого найденного сервиса создаётся экземпляр.

## Реестры сервисов

Фасад поддерживает два внутренних реестра:

| Реестр | Ключ | Значение |
|---|---|---|
| `_services_by_model` | класс SQLAlchemy-модели | сервис сущности |
| `_services_by_schema` | класс Pydantic-схемы | сервис сущности |

Регистрация по схемам выполняется отдельно для операций:

```text
create
get
update
delete
```

Это позволяет однозначно определить сервис по типизированной
Pydantic-схеме.

## Допустимые входные данные

Публичные CRUD-методы принимают:

- Pydantic-схему;
- SQLAlchemy ORM-объект;
- объект `Mapping`, включая обычный словарь.

Типизированная схема или ORM-объект являются предпочтительными вариантами.

Обычный словарь определяется по тому, схемам каких сервисов он соответствует.
Такой выбор может оказаться неоднозначным.

## Определение сервиса

### ORM-объект

Для ORM-объекта сервис определяется по классу модели.

Если модель не зарегистрирована, выбрасывается `UnknownServiceError`.

### Pydantic-схема

Для Pydantic-схемы сервис определяется по точному классу схемы и виду
операции.

### Mapping

Для словаря фасад пытается проверить данные схемами соответствующей операции
всех зарегистрированных сервисов.

Возможны три результата:

| Результат | Поведение |
|---|---|
| найден один сервис | операция продолжается |
| не найден ни один сервис | `UnknownServiceError` |
| найдено несколько сервисов | `AmbiguousServiceError` |

Например, фильтр `{"id": 1}` подходит нескольким сущностям и поэтому
считается неоднозначным.

## Иерархия исключений

```text
OrmServiceError
├── UnknownServiceError
└── AmbiguousServiceError
```

`OrmServiceError` также используется для ошибок конфигурации фасада и
операций импорта или экспорта.

Ошибки определения сервиса выбрасываются наружу. Ошибки валидации и
SQLAlchemy во многих CRUD-операциях преобразуются в специальные возвращаемые
значения.

## Сохранение изменений

Внутренний метод `_save()` определяет способ синхронизации с базой данных.

### `auto_commit=True`

После каждой операции записи выполняется:

```text
session.commit()
```

### `auto_commit=False`

После каждой операции записи выполняется:

```text
session.flush()
```

Это позволяет получить первичные ключи и проверить ограничения базы, сохраняя
возможность объединить несколько операций в одну внешнюю транзакцию.

При `SQLAlchemyError` выполняются:

1. `rollback()`;
2. запись исключения в журнал;
3. возврат `False` из `_save()`.

## Создание

Метод:

```text
create(data)
```

Порядок выполнения:

```text
Определение сервиса
        ↓
Валидация через CreateSchema
        ↓
Создание ORM-объекта
        ↓
session.add()
        ↓
commit() или flush()
        ↓
Возврат объекта
```

Результат:

| Ситуация | Результат |
|---|---|
| операция успешна | созданный ORM-объект |
| данные отклонены схемой | `None` |
| ошибка SQLAlchemy | `None` |
| сервис не определён | исключение `OrmServiceError` |

## Получение

Метод:

```text
get(filters)
```

Фасад:

1. определяет сервис;
2. строит `Select` через сервис сущности;
3. выполняет `session.scalars(stmt).all()`;
4. возвращает список ORM-объектов.

Результат:

| Ситуация | Результат |
|---|---|
| найдены записи | список ORM-объектов |
| записей нет | пустой список |
| фильтр отклонён | пустой список |
| ошибка SQLAlchemy | пустой список |
| сервис не определён | исключение `OrmServiceError` |

Пустой список не позволяет отличить отсутствие данных от ошибки выполнения
без анализа журнала.

## Обновление

Метод:

```text
update(filters_or_obj, data)
```

Цель обновления может быть задана:

- ORM-объектом;
- Pydantic-схемой фильтрации;
- словарём фильтра.

Если передан ORM-объект, обновляется непосредственно он.

В остальных случаях фасад сначала получает список объектов через `Select`,
после чего вызывает `apply_update()` выбранного сервиса для каждого объекта.

После изменения выполняется `commit()` или `flush()`.

Результат:

| Ситуация | Результат |
|---|---|
| операция успешна | список обновлённых ORM-объектов |
| объектов по фильтру нет | пустой список |
| фильтр или данные отклонены | `None` |
| ошибка сохранения | `None` |
| сервис не определён | исключение `OrmServiceError` |

Обновление выполняется над всеми объектами, найденными по фильтру.

## Удаление

Метод:

```text
delete(filters)
```

Поддерживаются два режима.

### Persistent ORM-объект

Если передан объект, уже связанный с текущей сессией, используется:

```text
session.delete(obj)
```

### Фильтр или transient ORM-объект

В остальных случаях сервис строит SQLAlchemy-выражение `Delete`, которое
выполняется через `session.execute()`.

Результат:

| Ситуация | Результат |
|---|---|
| операция успешна | количество удалённых записей |
| ничего не удалено | `0` |
| фильтр отклонён | `None` |
| ошибка SQLAlchemy | `None` |
| сервис не определён | исключение `OrmServiceError` |

## Явное управление транзакцией

### `commit()`

Подтверждает текущую транзакцию.

Возвращает:

- `True` при успехе;
- `False` при ошибке SQLAlchemy.

При ошибке автоматически выполняется `rollback()`.

### `rollback()`

Откатывает текущую транзакцию.

Метод не возвращает значение.

### `close()`

Закрывает текущую SQLAlchemy-сессию.

После закрытия экземпляр фасада не должен использоваться для новых операций.

## Context manager

`OrmService` поддерживает конструкцию:

```python
with OrmService(session_factory=factory) as orm_service:
    ...
```

При входе возвращается текущий экземпляр фасада.

При выходе:

| Ситуация | Поведение |
|---|---|
| внутри блока возникло исключение | выполняется `rollback()` |
| исключения нет и `auto_commit=True` | выполняется `commit()` |
| `close_on_exit=True` | сессия закрывается |

Исключения из блока не подавляются: `__exit__()` возвращает `False`.

Следует учитывать, что write-операции при `auto_commit=True` уже выполняют
`commit()` самостоятельно. Дополнительный `commit()` при выходе из блока
подтверждает оставшееся состояние сессии.

## XLSX-экспорт

Метод:

```text
export_to_xlsx(model_names, file_path)
```

Параметр `model_names` содержит имена моделей или листов.

При `model_names=None` выбираются все поддерживаемые сущности.

Порядок выполнения:

1. нормализация имён листов;
2. определение сервиса для каждого листа;
3. получение всех объектов выбранных моделей;
4. формирование словаря данных;
5. передача данных в `ImportExportService`;
6. возврат пути к созданному XLSX-файлу.

Ошибки нормализации, определения сервиса и получения данных преобразуются в
`OrmServiceError`.

## XLSX-импорт

Метод:

```text
import_from_xlsx(file_path, model_names=None)
```

Порядок выполнения:

1. чтение XLSX через `ImportExportService`;
2. нормализация и фильтрация выбранных листов;
3. определение сервиса по имени листа;
4. валидация каждой строки через `CreateSchema`;
5. создание ORM-объектов;
6. добавление объектов в текущую сессию;
7. единое сохранение импортированных данных.

Результатом является словарь:

```text
имя листа → количество импортированных записей
```

Отклонение хотя бы одной строки прерывает импорт и приводит к
`OrmServiceError`.

:::{admonition} Статус подсистемы
:class: warning

`OrmService` содержит рабочие точки интеграции с XLSX, однако подсистема
`app.io_tools` требует отдельного аудита. Контракты файлового обмена не
следует считать окончательно подтверждёнными.
:::

## Журналирование

Фасад записывает:

- начало и завершение операций;
- тип входного объекта;
- выбранную модель;
- количество найденных, обновлённых или удалённых объектов;
- отклонение входных данных;
- ошибки SQLAlchemy;
- действия `commit`, `flush`, `rollback` и `close`;
- ход импорта и экспорта.

При этом журнал является единственным источником детальной причины для ряда
операций, возвращающих `None` или пустой список.

## Сводка возвращаемых значений

| Метод | Успех | Отказ или ошибка |
|---|---|---|
| `create()` | ORM-объект | `None` |
| `get()` | список ORM-объектов | пустой список |
| `update()` | список ORM-объектов | `None` |
| `delete()` | количество удалённых записей | `None` |
| `commit()` | `True` | `False` |
| `rollback()` | `None` | исключение не перехватывается |
| `close()` | `None` | исключение не перехватывается |
| `export_to_xlsx()` | `Path` | `OrmServiceError` |
| `import_from_xlsx()` | `dict[str, int]` | `OrmServiceError` |

## Архитектурные ограничения

### Неоднородный контракт ошибок

CRUD-методы используют разные признаки отказа:

- `None`;
- пустой список;
- `False`;
- исключение.

Вызывающий код должен знать контракт каждого метода отдельно.

### Неоднозначность словарей

Mapping без явного типа может соответствовать нескольким схемам.

Для публичного кода рекомендуется использовать Pydantic-схемы или
ORM-объекты.

### Совмещение ответственностей

`OrmService` объединяет:

- обнаружение сервисов;
- маршрутизацию;
- CRUD;
- управление транзакциями;
- журналирование;
- XLSX-импорт;
- XLSX-экспорт.

Это увеличивает размер и связанность класса. Немедленное разделение не
требуется, но новые обязанности следует добавлять только после явного
архитектурного решения.

### Зависимость от динамического импорта

Новый сервис регистрируется автоматически только при выполнении всех
условий обнаружения.

Ошибки в структуре модуля или объявлении `model` могут привести к тому, что
сервис не будет зарегистрирован.

### Частичная потеря диагностической информации

Для `get()` ошибка и корректное отсутствие записей представлены одинаково:
пустым списком.

Для `create()`, `update()` и `delete()` подробность ошибки доступна только в
журнале.

## Рекомендации по использованию

- передавать типизированные Pydantic-схемы;
- проверять возвращаемое значение каждого write-метода;
- использовать `auto_commit=False` для составных операций;
- явно вызывать `commit()` после успешного завершения составной операции;
- выполнять `rollback()` при ошибке бизнес-сценария;
- не использовать фасад после `close()`;
- не полагаться на XLSX-контракты до завершения аудита `app.io_tools`.
