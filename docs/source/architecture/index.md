# Архитектура

Раздел описывает фактическую архитектуру backend DigitalDiaryApp на
зафиксированном baseline-коммите.

Основное внимание уделяется слоям моделей, схем и сервисов. Перспективные
продуктовые требования рассматриваются отдельно и не смешиваются с
описанием существующей реализации.

## Общая схема

```text
Пользовательский интерфейс и сценарии приложения
                    ↓
               OrmService
                    ↓
        Сервисы предметных сущностей
                    ↓
          Pydantic-схемы и валидация
                    ↓
            SQLAlchemy-модели
                    ↓
             Хранилище данных
```

## Основные слои

### Модели

Пакет `app.models` содержит SQLAlchemy-модели предметной области.

К основным сущностям относятся:

- учебная группа;
- студент;
- расписание;
- связь группы с расписанием;
- занятие;
- посещаемость;
- оценка;
- комментарий.

Модели определяют структуру хранения данных, внешние ключи, отношения,
ограничения уникальности и каскадное поведение.

### Схемы

Пакет `app.schemas` содержит Pydantic-схемы для проверки и передачи
данных.

Для предметных сущностей используются отдельные варианты схем для
создания, фильтрации, обновления и удаления.

Базовая конфигурация схем запрещает неизвестные поля, поддерживает
создание объектов из ORM-моделей, очищает строковые значения и выполняет
валидацию при изменении данных.

### Сервисы сущностей

Пакет `app.services` содержит сервисы, связанные с конкретными
SQLAlchemy-моделями и соответствующими Pydantic-схемами.

Сервисы:

- подготавливают ORM-объекты;
- проверяют входные данные;
- формируют SQLAlchemy-запросы;
- ограничивают изменяемые поля;
- инкапсулируют правила работы с отдельными сущностями.

Сервисы сущностей не должны самостоятельно владеть жизненным циклом
сессии и транзакции.

### OrmService

`OrmService` является фасадом над сервисным слоем и точкой выполнения
основных операций с хранилищем.

Он:

- обнаруживает и регистрирует сервисы сущностей;
- выбирает подходящий сервис по переданным данным;
- выполняет операции создания, получения, обновления и удаления;
- управляет SQLAlchemy-сессией;
- подтверждает и откатывает транзакции;
- предоставляет операции импорта и экспорта.

Передача типизированных Pydantic-схем предпочтительнее передачи обычных
словарей. Словарь может не содержать достаточно информации для
однозначного выбора сервиса.

## Поток выполнения операции

Типовая операция проходит следующие этапы:

```text
Входные данные
      ↓
Выбор сервиса сущности
      ↓
Проверка и нормализация данных
      ↓
Построение ORM-объекта или SQL-запроса
      ↓
Выполнение через SQLAlchemy-сессию
      ↓
Подтверждение или откат транзакции
      ↓
Возврат ORM-объекта, списка объектов или результата операции
```

## Ответственность за транзакции

Сервисы сущностей подготавливают данные и запросы, но не подтверждают
транзакции самостоятельно.

Управление транзакцией выполняется на уровне `OrmService`:

- `commit()` подтверждает изменения;
- `rollback()` отменяет текущую транзакцию;
- `close()` завершает работу с текущей сессией.

Такое разделение позволяет объединять несколько операций в одну
транзакцию, однако требует явного соблюдения контракта вызывающим кодом.

## Архитектурные свойства

Для текущей реализации характерны:

- единая базовая SQLAlchemy-модель;
- автоматическая регистрация моделей при импорте пакета;
- отдельные Pydantic-схемы для разных видов операций;
- отдельный сервис для каждой предметной сущности;
- общий фасад `OrmService`;
- ограничения уникальности на уровне базы данных;
- каскадное удаление связанных данных;
- автоматические временные поля создания и обновления.

## Известные ограничения

Текущая архитектура требует дальнейшего уточнения в следующих областях:

- контракты возврата и обработки ошибок неодинаковы для разных операций;
- обычные словари могут приводить к неоднозначному выбору сервиса;
- часть вспомогательных проверок формата не подключена к основным схемам;
- некоторые поля схем принимаются, но не применяются сервисами полностью;
- `OrmService` совмещает обнаружение сервисов, CRUD, транзакции,
  журналирование и файловый обмен;
- подсистема `app.io_tools` требует отдельного аудита.

Указанные ограничения не означают необходимость немедленного
рефакторинга. Сначала они должны быть описаны как явные архитектурные
контракты и подтверждены тестами.
