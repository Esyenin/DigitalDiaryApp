# DigitalDiaryApp

DigitalDiaryApp - локальное приложение-электронный дневник для преподавателя. Проект помогает вести учебные группы, студентов, расписание, занятия, посещаемость, оценки и комментарии к работе студентов.

Сейчас в репозитории уже собрана основа backend-части: ORM-модели, схемы валидации, сервисы сущностей, общий ORM-фасад и тестовая база. Это фундамент, на который дальше можно спокойно ставить UI для Windows, Linux и мобильных устройств.

## Что умеет проект сейчас

- хранить структуру учебных данных через SQLAlchemy-модели;
- валидировать входные данные через Pydantic-схемы;
- выполнять CRUD-операции через сервисы сущностей;
- работать через единый `OrmService` как через фасад над ORM-слоем;
- покрывать ключевую логику тестами;
- вести файловое логирование.

## Основные сущности

### Учебный Процесс

Settings / Academic structure: учебные годы, семестры, дисциплины, группы
курса, модули, выбор календаря и закрытие семестра. Настройки прежнего
календаря однократно переносятся из QSettings в БД, без назначения вымышленных
дисциплин старым занятиям. Новый шаблон расписания связывается с курсом;
версии сохраняют этот контекст, многогрупповые занятия относятся к одному курсу.

Settings / Teaching process: мероприятия и их стоимость, два независимых
семинарских теста, попытки и пересдачи, модульные суммы и задолженности,
версионные чек-листы защиты с таймером, консультации без фиксированной группы,
индивидуальные планы, календарные изменения и история посещаемости.
Из карточки занятия и профиля студента доступны соответствующие контексты.

Новые результаты хранятся отдельно от `Mark`: `AssessmentEvent`,
`AssessmentAttempt`, `ResultCorrection`. Баллы Decimal с точностью 0.01;
преподаватель выбирает максимум, обязательность и политику best/latest.
Финализированные попытки, ответы и корректировки неизменяемы. Повтор одной
операции не удваивает начисление. История защит хранит собственную версию
критериев. Присутствие и защита независимы, результат консультации относится
к исходному мероприятию и модулю.

Завершение переклички сохраняет UTC-время; последующий приход фиксирует
опоздание. Исправление посещаемости с причиной отделено от регистрации нового
прихода. Старое время с неизвестным часовым поясом не используется для точного
расчёта опозданий. Праздники и переносы не удаляют исходные занятия и результаты.

Полный типизированный XLSX-архив включает академические данные, попытки,
ответы, аудит и все прежние таблицы. Восстановление Standard Import атомарно
и допускается только в пустую БД. Smart остаётся импортом групп и студентов;
Template не подменяет полное восстановление истории.

Схема, алгоритмы, пользовательские сценарии, миграции и ограничения:
[TEACHING_PROCESS.md](TEACHING_PROCESS.md).

В проекте уже описаны следующие сущности:

- `Group` - учебная группа;
- `Student` - студент;
- `Schedule` - запись расписания;
- `ScheduleGroupLink` - связь группы с расписанием;
- `Lesson` - конкретное занятие;
- `Attendance` - посещаемость студента на занятии;
- `Mark` - оценка студента за занятие;
- `Comment` - комментарий преподавателя к занятию студента.
- `GroupMembership` - принадлежность студента к группе в периоде [start_date, end_date);
- `LessonParticipant` - доказанное участие или подтверждённый состав занятия.

### История расписания и студентов

`Schedule` хранит неизменяемые версии одной серии: `series_key`, `revision`,
`effective_from`, `effective_until`. Периоды версий не пересекаются. Изменение
действует с выбранной будущей даты; исторические ID и результаты сохраняются.
Заполненные будущие занятия блокируют переключение, удаление с историей
заменяется деактивацией.

Перевод закрывает прежний `GroupMembership` и открывает новый атомарно.
Студенты и группы архивируются вместо удаления истории. Состав завершённого
занятия не меняется при последующем переводе или архивировании студента.
Просмотр карточки и `students_for_lesson()` ничего не записывают. Команда
`Complete roll call` после подтверждения фиксирует состав и `roster_completed_at`.
До завершения переклички процент посещаемости не считается достоверным.

Миграции `app/ui/data/schedule_migration.py` и `membership_migration.py`
выполняются при открытии репозитория, транзакционно и повторяемо, без смены ID.
Для старых SQLite-баз предусмотрены резервные копии соответствующих этапов.
Перед обновлением используйте копию базы; тесты никогда не запускайте на рабочей.
Полный XLSX-архив включает периоды принадлежности, участников и время фиксации;
восстановление истории допускается только в пустую базу. Smart Import распознаёт
группы и студентов, но не восстанавливает историю переводов без даты.

Ограничения: неизвестные старые переводы не восстанавливаются задним числом.
Мигрированные периоды помечены `migrated_unknown`, старые результаты доказывают
только участие конкретных студентов, а не полноту состава. Старое время
завершения остаётся NULL. Автоматическое завершение неопределённой истории
запрещено. Даты переводов не содержат времени: несколько переводов за день
не позволяют определить группу на момент занятия; фиксация такого состава
блокируется. Уже подтверждённый до перевода состав сохраняется. Будущие
переводы и ручное разрешение неоднозначного состава пока не поддерживаются.

Исходные связи отражены в [app/DB_diagram.pdf](app/DB_diagram.pdf); новые
академические связи описаны в [TEACHING_PROCESS.md](TEACHING_PROCESS.md).

## Архитектура

Проект разделен на несколько слоев:

- `app/models` - ORM-модели базы данных;
- `app/schemas` - Pydantic-схемы для валидации данных;
- `app/services` - сервисы работы с конкретными сущностями;
- `app/services/ormservice.py` - единая точка входа в ORM-логику;
- `tests` - тесты моделей, схем, сервисов и ORM-фасада.

Такое разделение делает код более читаемым, расширяемым и удобным для подключения интерфейса в будущем.

## База данных

По умолчанию проект пытается использовать PostgreSQL.

Если настройки PostgreSQL не заданы полностью, приложение автоматически переключается на локальную SQLite-базу. Это удобно для локального запуска, прототипирования и разработки без обязательного поднятия PostgreSQL.

Настройки читаются из файла `.env` в корне проекта.

Основные параметры:

- `DB_USER`
- `DB_PASSWORD`
- `DB_HOST`
- `DB_PORT`
- `DB_NAME`
- `SQLITE_DB_PATH` - имя или путь к локальному SQLite-файлу, если используется fallback

## Установка

1. Клонировать репозиторий:

```powershell
git clone https://github.com/Esyenin/DigitalDiaryApp.git
cd DigitalDiaryApp
```

2. Создать виртуальное окружение:

```powershell
python -m venv .venv
```

3. Активировать виртуальное окружение:

Для Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

Для Windows cmd:

```cmd
.\.venv\Scripts\activate.bat
```

Для Linux:

```bash
source .venv/bin/activate
```

4. Установить зависимости:

```powershell
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

5. Создать файл `.env` в корне проекта.

Если хочешь работать через PostgreSQL, укажи в нем:

```env
DB_USER=your_user
DB_PASSWORD=your_password
DB_HOST=localhost
DB_PORT=5432
DB_NAME=digital_diary
```

Если PostgreSQL не настроен, можно не заполнять эти поля полностью. Тогда
проект автоматически переключится на SQLite и создаст локальный файл базы
данных.

При желании можно явно задать имя SQLite-файла:

```env
SQLITE_DB_PATH=digital_diary.db
```

6. Проверить, что установка прошла нормально:

```powershell
$env:DIGITAL_DIARY_TEST_DATABASE_URL = 'sqlite:///build/documentation-checks/test_setup_fresh.db'
New-Item -ItemType Directory -Path build/documentation-checks -Force | Out-Null
& .\.venv\Scripts\python.exe -m pytest tests -q --basetemp=build/documentation-checks/pytest
```

## Логирование

В проекте есть настройка файлового логирования.

Имя файла лога формируется в формате:

`ГГГГ-ММ-ДД_ЧЧ-ММ-СС_УРОВЕНЬ.log`

Пример:

`2026-05-10_15-42-18_INFO.log`

Внутри логов время записывается с миллисекундами.

## Тесты

Тесты покрывают:

- модели базы данных;
- схемы валидации;
- сервисы сущностей;
- `OrmService`;
- конфигурацию логирования.

Фикстура требует явную `DIGITAL_DIARY_TEST_DATABASE_URL`, имя файла/БД
с префиксом `test_`, отличие от рабочей базы и отсутствие таблиц. Она не удаляет
таблицы существующей БД. При повторном запуске выбирайте новый пустой файл.
Запуск всех тестов (переменные окружения действуют в текущем терминале):

```powershell
$env:DIGITAL_DIARY_TEST_DATABASE_URL = 'sqlite:///build/documentation-checks/test_suite_fresh.db'
New-Item -ItemType Directory -Path build/documentation-checks -Force | Out-Null
& .\.venv\Scripts\python.exe -m pytest tests -q --basetemp=build/documentation-checks/pytest
```

## Технологии

PostgreSQL-интеграции запускаются только с отдельно выделенными пустыми БД:
`DIGITAL_DIARY_MEMBERSHIP_POSTGRES_URL` для истории состава и
`DIGITAL_DIARY_SCHEDULE_POSTGRES_URL` для расписания (см. тесты PostgreSQL).
Для учебных операций используется `DIGITAL_DIARY_EDUCATION_POSTGRESQL_URL`.
Не указывайте рабочие подключения. Без этих настроек интеграции пропускаются,
и SQLite-прогон не подтверждает работоспособность PostgreSQL-триггеров.

## Цель проекта

Цель DigitalDiaryApp - дать преподавателю удобный локальный инструмент для повседневной работы с учебным процессом: от ведения списка студентов и расписания до фиксации посещаемости, оценок и комментариев по каждому занятию.

Проект развивается с упором на три вещи:

- читаемость кода;
- масштабируемость архитектуры;
- понятность для дальнейшей поддержки и развития.
